# 业内采集最佳实践（2026-10 核对）

范围：新闻/文章类采集的发现、抽取、调度、去重。结论按 ponytail 口径写：只留能长期维护的部分。

## 一句话

能跑几年的新闻采集栈就两样东西：**每站一条发现规则（sitemap / RSS / API）+ 一个通用正文抽取器**。所有"通用爬虫框架"到了真实站点都会退化成 per-site 配置——这不是我们能力不够，是行业现状。

## 1. 发现层：sitemap / RSS 优先，HTML 列表兜底

- **Fundus**（Humboldt，ACL 2024 demo，479★）就是这个模型的学术版：每个 publisher 一个模块，URL 来源是 sitemap / feed，只做静态新闻页。它不假装能"通用"。[repo](https://github.com/flairNLP/fundus)
- **news-please**（2.5k★，曾经的"just works"标准答案）**已于 2026-04 归档**（archived=true）。别押注老项目。
- 实践口径：
  - sitemap 用 `lastmod` 做增量；RSS 只覆盖最近窗口（10–50 条），拿不到历史；
  - Google News sitemap 只有最近 2 天，不能当档案；
  - HTML 列表页是最后手段，因为分页规则每站都不一样，这是必须写 per-site 配置的地方。

## 2. 抽取层：trafilatura 是默认答案，但有两个坑

- **维护状态**：trafilatura 2.3.1（2026-10-06 发布），活跃；多个第三方评测里排第一（ScrapingHub 的 article extraction benchmark、Lejeune & Barbaresi 的对比）。
- **newspaper3k 事实死亡**：最后一次发版 **2018-09-28**，513 个 open issue；newspaper4k 是社区续命分支（0.9.6 / 2026-07）。
- **坑 1（直接命中我们的格式）**：trafilatura **默认丢弃 iframe**，[issue #175](https://github.com/adbar/trafilatura/issues/175) 里作者明确说是 by design，至今没加参数。YouTube / Spotify 嵌入全丢 → 我们的 `video`、`link` 两列必须自己从原始 HTML 抽 iframe。这是本次调研最有价值的一条。
- **坑 2**：多作者只取一个（[#92](https://github.com/adbar/trafilatura/issues/92)、[#24](https://github.com/adbar/trafilatura/issues/24)），无 meta 时靠启发式 → `user_author_name` 要先用 JSON-LD / `meta[name=author]` 兜底，再退回 trafilatura。

## 3. 浏览器 / LLM 框架：能力强，运维债更重

| 项目 | 规模 | issue 里反复出现的问题 | 对我们的结论 |
|---|---|---|---|
| crawl4ai | 86k★ | Docker 内存泄漏、chrome 进程残留（[#1256](https://github.com/unclecode/crawl4ai/issues/1256) open、#943、#980、#1608） | 适合"少量、要交互"的页；不适合几十万静态页 |
| firecrawl | 195k★ | 自托管 Redis 限流故障、依赖漂移（#3728、#4104、#4050） | 云版按 credit 计费：$83/月 10 万页、$333/月 50 万页 |
| scrapy | 65k★ | 无重大坑，但对我们 109 个异构小站是过度工程 | 只用它的参数（AutoThrottle / ROBOTSTXT_OBEY） |

## 4. 礼貌与稳定性

- 并发**按域名**限（1–2 req/s），失败指数退避；遵守 `Crawl-delay` 和 429 的 `Retry-After`。
- 条件请求（ETag / If-Modified-Since）能省掉大量重复传输，尤其政府站。
- 本次实测：太平洋小站多是共享主机，2 req/s 都可能触发超时；建议按域 1 req/s、超时重试 2 次。

## 5. 去重与增量

- 稳定 ID：WP `post.id` / RSS `guid`；没有则 canonical URL；入库再加 content hash。
- 增量：WP `modified_after`、sitemap `lastmod`、RSS 窗口。
- 断点：按站记游标（页码 / lastmod / guid），失败不推进游标。

## 对我们方案的修订（原 → 改）

| # | 原方案 | 修订 | 理由 |
|---|---|---|---|
| 1 | 直连层：requests + trafilatura + 每站配置 | **保留** | 就是 Fundus 的做法，行业验证过 |
| 2 | 正文抽取一把梭 | **加 iframe / embed 单独抽取** | trafilatura 不给（#175），但格式要 `video`/`link` |
| 3 | 难站上浏览器 | **只在 8 个 CF 站用 ego-browser，不引入 crawl4ai** | 内存泄漏 issue 太多，页数少才划算 |
| 4 | Firecrawl 当第二层 | **降级为兜底：同站连续失败 3 次才升级** | 300k 页 ≈ $300/月，常规路径不该花钱 |
| 5 | REA 当"付费墙层" | **REA 只用于 1–2 个无列表页/接口藏得深的站** | 这份清单没有硬付费墙（lefigaro 除外且该删） |
| 6 | 先全量 | **先 3 个站最小实现（WP / sitemap / HTML 各一）** | 把 iframe、日期、作者三个坑一次踩掉再复制 |

## 一句话结论

行业最佳实践不是"更强的爬虫"，是"**更少的假设 + 每站一份配置**"。我们原方案方向对，只需要把 Firecrawl 从常规路径降级为兜底、把 iframe 坑补上。
